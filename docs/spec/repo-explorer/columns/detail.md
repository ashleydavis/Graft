# Columns in the repo explorer

## Overview

The repo explorer page shows its panes side by side in columns. The first is the repo details pane (see [repo-details](../repo-details/detail.md)), whose Commits link opens the commit pane, which holds the commit list, to its right. Clicking a commit opens the commit details pane to its right and clicking one of the commit's changed files opens the file pane to the right of that. The commit details pane's "Commit details" row opens the commit's message and facts in the "Commit details" pane, in the file pane's place. Each pane is a rounded card with a header, styled as the Graft style guide's commit explorer is, in the light and dark themes. The file pane shows the diff as rows with old and new line numbers.

## Behaviour

- The repo details pane is always the first column and the commit pane the second while it is open. Each keeps its full width and always shows in full. When the panes are wider than the window, the page scrolls sideways. The commit list scrolls inside the commit pane when it is taller than the window.
- Each row of the commit pane shows the commit's title (cut short with an ellipsis when it is too long), its refs, its author's name, its author date as a short date and the first seven characters of its hash. The title comes first and the refs sit after it in a narrow column of their own, as in the style guide's commit list, so the title always keeps its room and the author, date and hash line up from row to row. Each ref is a badge with its kind's icon: the checked-out branch filled in the accent colour and named without "HEAD -> ", a remote branch, a tag named without "tag: " and any other branch. The column shows only the badges that fit its width, in git's order, worked out from the measured widths of the column and the badges. When some are left out it shows a "…" button after them, whose tooltip shows how many more there are, and the first badge always shows, cut short with an ellipsis when it alone is too wide. Clicking "…" opens a drop-down under it listing every badge of the commit, in the style guide's ref badge look, and the selected and open commits stay as they were. The drop-down closes on Escape or a click outside it. Hovering a commit's title shows it in a tooltip. The selected commit has the selected background, and the commit whose details are open has a bar on its left edge and a bold title (see [keys](../keys/detail.md)).
- A header row above the commit list's scrolling area names its columns: Message over the titles, Author, Date and Hash, each lined up with its column in the rows. Over the badges' column the header row leaves a blank space of the same width. The header row stays in view as the list scrolls. It is styled as the style guide's table header: small muted text of medium weight with a border under it, in the light and dark themes.
- The commit list is a virtual list built with TanStack Virtual (`@tanstack/react-virtual`, locked to an exact version in `package.json`). It draws only the rows in view and a few either side, so a repo with any number of commits scrolls smoothly.
- The commit pane reads the commits a page at a time, newest first, with the commits task. The page size is `COMMIT_PAGE_SIZE` in `frontend/src/lib/commit-pages.ts`. The list covers every local branch, every remote-tracking branch and HEAD, so a commit that only another branch reaches is listed with that branch's badge. The list leaves stashes out. Opening the commit pane reads the first page, `git log --no-show-signature --max-count=<page size> --branches --remotes HEAD --`, and reads it afresh each time the pane opens. When the last row the list draws comes within `NEAR_END_ROW_COUNT` rows of the last commit read, the pane reads the next page and adds it under the commits already listed. Each page after the first runs `git log --no-show-signature --max-count=<page size> --skip=<count read> --branches --remotes HEAD --`: it starts from the same branches and HEAD and skips the commits already read. So the pages list every commit of every branch once, the commits from both sides of a merge included, and scrolling to the end reaches the first commit of each branch's history. When a branch moves on between two pages, git can list a commit again, and the pane leaves out a commit it has already listed. It reads one page at a time. A page with fewer commits than the page size ends at the first commit of every branch's history, so it is the last page the pane reads.
- While a page is read, grey placeholder rows show under the last commit, drawn with MaterialUI's `Skeleton` as the style guide's loading placeholder is. Each is the height of a commit row, with grey blocks where the title, author, date and hash go, in the style guide's colours in the light and dark themes. Before the first page is read they fill the visible part of the list. The list is marked busy for assistive technology while a page is read. When a page could not be read, an error row under the commits shows why, the commits already read stay listed and the pane reads the next page only after it opens again.
- Once the last page has been read, an end of list row under the last commit shows "That is every commit.". In a repo with no commits the list shows only "There are no commits.". The row is in muted text in the small text size, with the style guide's tokens in the light and dark themes (`--space-2` above and below, `--space-4` either side and at least `--space-8` tall), as the style guide's commit pane shows it. Its `data-id` is `commits-end` or `commits-none`. It shows only while no page is being read and the last read succeeded.
- A page read before the commit pane closed and opened again is dropped, so the list shows only the pages read since the pane last opened.
- Dates are shown in the locale and time zone of the system Graft runs on.
- Clicking a commit in the commit pane opens the commit details pane to its right. Clicking a commit while the file pane is open closes the file pane.
- The commit details pane is headed "Commit" with the short hash beside it. At its top is a "Commit details" row with the style guide's message icon. Like a file row, it is a MaterialUI `ListItemButton` with the hover and selected colours, and it has a bar on its left edge while its pane is open. The commit's message and facts are in the "Commit details" pane.
- Clicking the "Commit details" row selects it and opens the "Commit details" pane to the right of the commit details pane, in place of any open file pane, as wide as the file pane. It is headed "Commit details", has a close button and shows the commit's full message (the title in bold, then the description when there is one) and a list of facts, each labelled: "Authored" with the author's name, email and the date and time, "Committed" with the committer's name, email and the date and time, "Hash" with the full hash and "Parent" or "Parents" with the parents as short hashes ("None, this is the first commit" for the first commit). It shows the commit the commit details pane read, without reading it again. Opening a changed file closes the "Commit details" pane and opens the file pane in its place.
- Under a "Files changed (<count>)" heading it lists the files the commit changed, each with its file icon and its path, the directory muted. Hovering a file shows a tooltip with git's one letter change type in its colour (A green, D red, M or T orange) and its name, the lines the commit added and deleted ("+1 −1"), or "Binary file" for a binary file, what the change means and the path. A commit with no changed files, such as a merge, shows "No files changed in this commit.". The selected file has the selected background and the file whose diff is open has a bar on its left edge.
- Clicking a changed file opens the file pane to the right of the commit details pane. It is headed by the file's icon and the file's name, with the full path in the title's tooltip, and shows every line of the file's diff in the commit as git writes it, as rows: an added or removed line on its diff colour with its old and new line numbers and a "+" or "−" marker, a hunk header as a muted bar and git's own header lines muted.
- Every file path Graft shows has the file path menu button beside it, as in the style guide: the file pane's title bar and each changed file row of the commit details pane, and the changes pane's rows (see [changes](../changes/detail.md)). The button shows a copy icon and a small chevron. On a row it shows while the row is under the pointer, selected or holds the keyboard, and it keeps its space when hidden, so the path never shifts. Clicking it opens a menu under it with "Copy full file path" (the repo's path joined with the file's path), "Copy relative file path" (the path from the repo's root), "Copy file name", a divider, the file manager item and "Open in editor". The file manager item is named for the platform Ziggy reports: "Reveal in Finder" on macOS, "Show in Explorer" on Windows and "Open in file manager" on Linux.
- A copy item copies its text to the clipboard and closes the menu, and the button shows a tick in the success colour for a moment, as the style guide's copy button does.
- The file manager item queues the show file in file manager task. It opens Finder with the file selected on macOS (`open -R <file>`), Explorer with the file selected on Windows (`explorer /select,<file>`) and the file manager on the file's directory on Linux (`xdg-open <directory>`). "Open in editor" queues the open file in editor task, which runs the command the `editor` setting in Graft's config file names, with the file's full path as its last argument. The setting is split at its spaces, so `code --reuse-window` works. With no `editor` setting it opens the file with the operating system's default app for its type: `open <file>` on macOS, `explorer <file>` on Windows and `xdg-open <file>` on Linux. The task reads the setting each time, so a change to it takes effect without a restart.
- Both tasks start their program through the backend's program starter. A file that is no longer in the working tree, a program that cannot start and a program that exits with an error each fail the task, and the menu shows the backend's text under its items, which names the command it ran and what the program wrote to its standard error. The menu closes once the file is opened.
- A click on the button or its menu stays with them, so it never selects or opens the row the button sits in. Escape or Tab closes the menu and puts the keyboard back on the button, and a click outside closes it.
- The file pane takes the width the panes to its left leave over, so it reaches the right edge of the page while no pane is maximised, and is never narrower than 840 pixels, or than the page's visible area less its margins in a window narrower than that. When the panes need more than the window's width, it is that least width and the page scrolls sideways. Its width follows the window as it is resized and as panes open and close to its left.
- When a pane opens beyond the right edge of the window, the page scrolls sideways, smoothly and by the least amount needed, until the pane is in view. A pane that opens already in view leaves the page where it is.
- Each pane after the repo details pane animates as it opens and as it closes, over the style guide's normal duration (`--duration-normal`) with its standard easing (`--ease-standard`). An opening pane fades in. A closing pane stays drawn while it fades out and its column narrows to nothing, so the panes to its right slide left into its place, and then it goes. Opening another commit's details, another file's diff or the "Commit details" pane in a file pane's place fades the pane in afresh.
- The keys and clicks act on the open panes while a pane animates. A closing pane ignores clicks and gives up the focus. A pane that is closing opens again at once when the user opens it again, such as with Enter after Escape closed it.
- While the system's reduced motion setting is on, the panes open and close at once.
- Each of the commit pane, the commit details pane, the "Commit details" pane and the file pane has a close button (an X icon with a "Close" tooltip) at the right of its header. Closing the file pane or the "Commit details" pane leaves the commit details pane open. Closing the commit details pane closes the file pane or the "Commit details" pane with it. Closing the commit pane closes the commit details pane and the file pane or the "Commit details" pane with it, as Escape in the commit pane does, and makes the repo details pane active with the Commits link still selected. The breadcrumb trail drops the steps of the panes that closed.
- Every pane has a maximise button in its header: the repo details pane, the commit pane, the commit details pane, the changes pane and the file pane, for a commit's file and for a working file. In a pane with a close button it sits just before the close button. It is the style guide's maximise button: an icon button with arrows pointing out (Font Awesome's `up-right-and-down-left-from-center`) while the pane is at its usual size and arrows pointing in (`down-left-and-up-right-to-center`) while it is maximised. Its tooltip shows "Maximise the pane" or "Restore the pane" in bold, with "Key: M" under it, and the button is named the same for assistive technology. It follows the light and dark themes.
- Clicking the maximise button, or pressing M while the pane is active (see [keys](../keys/detail.md)), maximises the pane: it fills the repo explorer's width and the other panes are hidden. The maximised pane becomes and stays the active pane. Clicking the button again, or pressing M again, puts every pane back as it was, with its selection, scroll position and content, and scrolls the page to show the active pane. The hidden panes stay drawn while they are hidden, so each shows again with the content it had.
- Hiding and showing a pane for a maximised pane never starts its opening or closing animation.
- While a pane is maximised, clicking its items does what it always does. A pane opened that way to its right is hidden until the panes are put back. A change that makes another pane active, such as Enter opening the next pane, puts every pane back.
- Closing the maximised pane, with its close button or Escape, puts the other panes back.
- Every pane, the repo details pane, the commit pane, the commit details pane, the "Commit details" pane, the changes pane and the file pane (of a commit's file and of a working file), has a collapse button with a chevron pointing left in its header, before the maximise button and the close button where the pane has them, and hidden while the pane is maximised. Its tooltip reads "Collapse the pane to the left" with "Key: C" under it. Clicking it, or pressing C while the pane is active (see [keys](../keys/detail.md)), folds the pane into a strip the width of a button, drawn in the pane's place with its rounded card and border, as in the style guide's collapsed strip. The strip has a restore button with a chevron pointing right at its top, whose tooltip reads "Restore the pane" with "Key: C" under it, and the pane's title written down it in muted bold text: "Repo" and the repo's name, "Commits", "Commit" and the short hash, "Changes" for the changes pane, "Commit details" for the "Commit details" pane, or the file's name. Clicking the restore button restores the pane as it was. A collapsed pane keeps its place among the panes, and a pane that closes while collapsed opens in full the next time it opens. A collapsed commit details pane still reads its commit, so it shows it at once when restored. Opening the Commits or Changes link afresh opens its panes in full, and the repo details pane stays collapsed when it was.
- Each pane with a pane open to its right has a resize handle in the gap between them: the repo details pane, the commit pane, the commit details pane and the changes pane. The file pane, always the last pane, has none. The handle is a strip as wide as the gap with a line down its middle, which shows in the accent colour (`--color-select-pane`) under the pointer, while dragging and while the handle has the keyboard focus, as the style guide's resize handle does in the light and dark themes. The pointer over it is the column resize pointer.
- Dragging a handle moves the right edge of the pane to its left with the pointer. With a handle focused, Left makes the pane 16 pixels narrower and Right 16 pixels wider, and the repo explorer leaves those two keys to the handle. Double-clicking a handle puts the pane back to its usual width. A click on a handle makes no pane active.
- A pane never goes narrower or wider than its limits: 300 to 800 pixels for the repo details pane, 320 to 1000 pixels for the commit pane, 300 to 800 pixels for the commit details pane and 300 to 800 pixels for the changes pane. The commit pane's and the commit details pane's limits are the style guide's. The style guide gives none for the repo details pane or the changes pane, so they take the commit details pane's.
- The handle's tooltip says "Resize the <pane>", such as "Resize the commit pane", and "Drag, or use Left and Right. Double-click to reset.". For assistive technology it is a vertical separator named "Resize the <pane>", with the pane's limits as its least and greatest values.
- Each pane's width is saved in Graft's state file at `paneWidths.<pane>` (`repoDetails`, `commits`, `commitDetails` or `changes`) each time it changes, and the next run of Graft opens the pane at the saved width, kept inside the pane's limits. A double-click removes the saved width. A failed read or write of the state file is logged, and the pane keeps the width it shows.
- While a pane's task runs it says "Loading the commit." or "Loading the diff.". When the task fails the pane shows why.
- The commit details pane queues the commit details task, a background task that runs the `log` wrapper for the commit's details and the `diff-tree` wrapper for its changed files.
- The `log` wrapper reads one commit with `git log -z --no-show-signature --max-count=1 <hash> --` and the same `--format` string the commit pane uses. `--no-show-signature` stops `log.showSignature=true` in the user's git config adding signature text that the wrapper cannot read, so a signed commit's details show. The `--` after the hash makes git read it only as a commit, so `git log` reads the commit even when a file in the repo has the hash as its name.
- The `diff-tree` wrapper reads the changed files with `git diff-tree -r -z --root --no-commit-id --name-status <hash> --`, which compares the commit with its first parent, or with an empty tree for the first commit. git lists no changed files for a merge commit. It reads each file's line counts with the same command and `--numstat` in place of `--name-status`, because git writes only one of the two when given both. It refuses line counts that are not for the same files in the same order.
- Every `git log` and `git diff-tree` that reads a commit puts `--` straight after the hash, so git reads the hash only as a commit, even when a file in the repo has the hash as its name. Without it git stops with "ambiguous argument".
- The file pane queues the file diff task, a background task that runs the `diff-tree` wrapper for the file's diff with `git diff-tree -r -p --root --no-commit-id <hash> -- :(literal)<path>`. The `:(literal)` makes git read the path as it is, with `*`, `?` and `[` in it read as those characters: opening `foo[1].txt` shows its diff alone. The help panel shows the path without `:(literal)`.
- Both wrappers start `git` through the Git interface function. They refuse a hash that is not hexadecimal and an empty file path without starting `git`.
- The commits, commit details and file diff tasks refuse a request with an empty repo path with an error, before starting `git`. The task fails with the text "The repo path is empty. Give the path of the repo to read." and the backend keeps running and handles the next message. Graft itself always sends the path of the open repo, so the text shows only to a smoke test that sends an empty path.

## Acceptance criteria

- [x] The repo explorer page shows the commit pane, which wraps the commit list.
- [x] Clicking a commit opens the commit details pane to the right of the commit pane, with the commit's details and changed files.
- [x] Clicking a changed file opens the file pane to the right of the commit details pane, with the file's detail.
- [x] The commit details pane and the file pane can each be closed.
- [x] The commit pane's close button closes it and the panes to its right, makes the repo details pane active with the Commits link still selected and drops the closed panes' steps from the breadcrumb trail.
- [x] With `log.showSignature=true` in the git config, the commit details pane shows a signed commit with no error.
- [x] New Git wrappers call the Git interface function and new Ziggy background tasks run them to get the commit's details, changed files and the file's detail.
- [x] The first columns, the repo details pane and the commit pane, always show in full.
- [x] The panes are styled as in the Graft style guide, in the light and dark themes, without the style guide's other features.
- [x] The commit pane shows each commit's title, short hash, author, date and refs.
- [x] The commit details pane and its "Commit details" pane show the full message, author, committer, dates, parents and the changed files, with each file's change type and line counts in its tooltip.
- [x] The commit details pane shows a "Commit details" row at its top, above "Files changed (<count>)", with the style guide's message icon, as a `ListItemButton` like the file rows, and leaves the message and the facts to the "Commit details" pane.
